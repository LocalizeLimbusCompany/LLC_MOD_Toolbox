# 性能与架构排查（2026-11-08）

后续的配置命名、公告 ViewModel、依赖注册与生命周期调整见 [架构与命名](architecture.md)。本文保留启动优化时的分析记录；下方待办中的公告拆分、计时器释放、遥测取消源释放和配置文件写入已在后续部分处理。

本轮优先处理启动时的网络长尾等待、首屏前的同步初始化和重复图片解码。依据是代码路径与资源统计；Linux 环境不能运行 WPF，不能把请求预算或静态分析当成 Windows 启动时间实测。

| 优先级 | 已确认的问题 | 影响与本轮处理 |
| --- | --- | --- |
| P0 | `HttpService.GetTextAsync` 默认使用 `HttpClient` 的 100 秒超时，最多尝试 3 次 | 单个失联接口可能等待约 300.6 秒。元数据请求现在最多尝试 2 次，共用 8 秒预算，取消实际 HTTP 请求及重试等待；安装包下载保留原策略。 |
| P0 | `InitializeAsync` 等待工具箱检查完成后才开始模组版本检查 | 两段网络等待可能相加，极端情况下仅这两段就约 601 秒。现在节点和游戏路径准备后并行检查工具箱版本、公告和模组版本，保留更新确认、公告与自动安装的决策顺序。 |
| P0 | 远端皮肤列表、过期文案更新和 DNS 检查都会延长全局加载遮罩 | 皮肤列表首次进入皮肤页再取，本地皮肤先显示；文案只读本地缓存，界面就绪后刷新；DNS 检查移到后台并限制为 3 秒。彩蛋图片首次进入彩蛋页再取。 |
| P1 | `Loaded` 处理器在首次 `await` 前同步读皮肤、解码图片和初始化节点 | 改为首次 `ContentRendered` 后初始化，并让出 Dispatcher；初始遮罩保持开启。自定义皮肤仍可能在第一帧默认皮肤之后出现，需在 Windows 确认可接受。 |

| P1 | CI 的 `release.yml` 构建 `Release`，但该配置明确设置 `Optimize=False` | 已开启 Release 编译优化。`ReleaseLLCMT` 原本已经开启。 |
| P1 | 原有“启动总耗时”从 `Loaded` 内开始计时 | 漏掉配置、依赖解析和窗口构建，难以定位首屏问题。新增从 `App.OnStartup` 起算的阶段日志。 |
| P2 | `NodeList.json` 相对当前工作目录读取 | 从快捷方式或其他工作目录启动可能失败，改为基于应用目录读取；已确认且未变化的游戏路径也不再每次重写配置。 |

新的启动流程：配置及协议 → 创建窗口并显示第一帧 → 应用皮肤/初始化节点/确定游戏路径 → 并行必要检查 → 按原有规则处理更新、公告与自动安装 → 解除遮罩 → 刷新附加内容。8 秒是每次元数据调用的总预算，不是整个启动过程的上限；用户操作、首次协议、磁盘访问、兼容层、公告确认和自动安装仍可能增加耗时。超时仍沿用原来的“获取失败/无检查结果”回退行为；弱网下超过预算的更新和公告可能本次无法获取。

图片缓存主要减少重复打开文件、解码和对象分配。按 32 位像素估算，默认皮肤这些绑定由约 27.97 MiB 像素数据降至约 26.64 MiB，不能声称大幅减少整体内存。更大的内存来源包括 `GachaBackground.png`（1890×990，约 7.1 MiB）及 `B.png`、`W.png`（各约 5 MiB）。后续可按显示尺寸和 DPI 设置解码大小。字体已使用子集，三个子集文件合计约 1.47 MiB；继续裁剪字体不是本轮首要问题。

仍需处理的架构问题：

1. **主窗口一次创建 10 个功能页面。** `Collapsed` 只影响布局/显示，并不阻止 XAML 构造。建议改成页面工厂和内容宿主，首次导航时创建，并按需要保留页面状态。但 `SkinManager.BuildTreeIndex` 遍历现有控件树，严格校验 `host/element`，且 `MainWindow` 直接访问抽卡和彩蛋控件。应先支持页面注册、页面级换肤与延迟验证，再改页面懒加载，否则已有皮肤会报元素缺失。
2. **主 ViewModel 承担过多业务。** 构造器依赖 17 项服务，导航、启动、安装、公告、配置、皮肤和抽卡集中在一个对象。本轮把启动编排放入独立 partial 文件以便审查，但这不等于依赖解耦。下一步拆分 `InstallViewModel`、`SkinViewModel`、`AnnouncementViewModel`，由启动协调器输出阶段结果。
3. **服务层仍依赖 UI 和全局可变状态。** `HttpService`、`MirrorChyanService` 直接弹窗；`SkinService` 包装静态 `SkinManager.Instance`；`AppState`、`ConfigurationManager.Settings` 到处可写。错误应逐步作为结果交还 UI，启动检查应使用固定的节点/模式快照，避免并发检查中修改 Mirror 模式或弹窗重入。
4. **生命周期缺少统一取消与释放。** 安装有取消参数，但下载接口没有贯穿传递；`StopInstallAsync` 依赖标志位。文案定时器没有保存引用，部分 ViewModel 事件没有退订。`App.StartTelemetry` 在任务结束时释放 CTS，但 `OnExit` 仍可能对它调用 `Cancel`。建议建立应用/窗口生命周期令牌，统一停止计时器、观察后台任务与释放资源。本轮 HTTP 已支持令牌，尚未全链路接入。
5. **部分耗时文件操作仍在 UI 续体执行。** 皮肤下载完成后的解压、工具箱更新包的 SHA256 校验、字体复制、卸载可能阻塞界面。应在文件服务层提供可等待的后台执行及进度，保留 UI 更新在 Dispatcher。
6. **配置写入存在竞争。** `SaveConfig` 直接覆盖文件且未使用读配置时的锁，遥测后台与 UI 同时保存可能冲突。需要串行写入、临时文件替换和明确的配置所有权；不宜通过给所有配置读写简单包一层 `Task.Run` 处理。
7. **本地路径和兼容迁移仍同步执行。** Steam 库在慢盘或网络挂载盘上时，可把路径发现和验证移到后台，把目录选择弹窗保留在 UI。`LegacyStructureAdapter` 的确认分支与提示文字也存在反向行为，应独立修复并覆盖迁移测试。
